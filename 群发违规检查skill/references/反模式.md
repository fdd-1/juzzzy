# 反模式黑名单

历史踩过的坑，全部禁止再做。这个清单的目的是让接手者不要重复犯同样的错。

## 1. ❌ 把非续费场景纳入统计

**禁止**：把 `转介绍 / 拓美术 / 拓叫叫 / 拓英语 / 唤醒` 等场景的违规算进总数。
**为什么**：业务方只看续费违规，混入会让违规数看起来虚高，团队会被误伤。
**怎么避免**：`check.py` 默认只保留 `场景` 列包含「续费」的行；不要随便扩大 `KEEP_SCENE`。

## 2. ❌ 在脚本或文档里写绝对路径

**禁止**：`C:\Users\<具体用户名>\Desktop\...` 这种路径出现在任何地方（代码、SKILL.md、流程.md、注释）。
**为什么**：换一台电脑、换一个用户名、把文件夹放到 D 盘，全部失效。这个 skill 要能裸交接给任何人。
**怎么避免**：
- 代码：`Path(__file__).parent` 拼相对路径；外部资源用 `Path.home()` 拼。
- 文档：用 `<SKILL_DIR>` 占位。
- 自查：搜索 `C:\\Users` 应该没有任何命中。

## 3. ❌ 直接把 BI 行数当违规数

**禁止**：跳过过滤链路，BI 表多少行就报多少违规。
**为什么**：BI 原始表里包含转介绍 / 报备命中 / 同模板重复 / 合计行，不过滤会严重虚高。
**怎么避免**：必须依次跑完：去空 LP / 去合计 → 续费过滤 → 相似度剔除 → 同 LP 同文本去重，再统计。

## 4. ❌ 跳过相似度过滤直接播报

**禁止**：报备文档没更新就跳过 `check.py` 的相似度环节，或直接拿 BI 违规行播报。
**为什么**：阈值是 0.9，已报备的合规模板也会被算成违规，会冤枉到 LP。
**怎么避免**：`run.py` 的链路里 `check.py` 不能跳过；阈值由 `--threshold` 控制，不要硬改 < 0.8。

## 5. ❌ 复用旧的明细 Excel

**禁止**：用上次跑的 `海外LP群发违规明细.xlsx` 直接出统计。
**为什么**：数据范围、违规口径、新增 LP 都会变；用户全局规则也明确要求每次重新下载报表。
**怎么避免**：默认走 `run.py` 重新调 `bi_skill` 下载；除非用户明确说「这个文件我已经下载了」。

## 6. ❌ 同 LP 同文本按发送次数计数

**禁止**：同一个 LP 把同一段违规模板发了 50 次，就报 50 条违规。
**为什么**：群发场景下一条模板会扩散到几十个用户，按发送条数会把违规数放大几十倍。
**怎么避免**：`drop_duplicates([LP姓名, 归一化文本])` 一定要保留；同一 LP 同一文本永远算 1 次。

## 7. ❌ 把「合计 / 总计 / 小计」行当 LP

**禁止**：BI 表底部的合计行被当成 LP 名字进入统计。
**为什么**：合计行的违规数本身就是其他行加出来的，会重复计。
**怎么避免**：`check.py` 已对 LP 列过滤 `总计|小计|合计`，新增其他汇总关键字（如 `总和`）时同步加进来。

## 8. ❌ 静默吞掉数据链路异常

**禁止**：`check.py` 自检表显示某一步为 0 / 续费占比异常 / 行数对不上时仍继续写文件、播报。
**为什么**：BI 报表改字段、续费列被改名、文档掉权限——这些情况都会让链路某一步突然崩塌，静默通过会发出错误的钉钉播报。
**怎么避免**：自检不通过 → `sys.exit(2)`；`run.py` 透传退出码；播报只在自检通过后执行。
